

**String Immutability** is one of the **most frequently asked Java interview topics** for **3–10 YOE**. Interviewers often ask:

- What is immutability?
- Why is `String` immutable?
- How is `String` immutable internally?
- Why is immutability important for `HashMap`?
- How does immutability help with the String Pool?
- Can we make a String mutable?

---

# 1. What is Immutable?

An object is **immutable** if **its state cannot be changed after it is created**.

Once an immutable object is constructed, its data remains fixed.

---

## Example

```
String s = "Java";

s.concat(" Programming");

System.out.println(s);
```

Output

```
Java
```

The original object is **not modified**.

---

## Correct Way

```
String s = "Java";

s = s.concat(" Programming");

System.out.println(s);
```

Output

```
Java Programming
```

A **new String object** is created, and `s` now points to it.

---

## Memory Diagram

Before

```
Stack                 String Pool

s ---------------> "Java"
```

After

```
s = s.concat(" Programming");
```

```
Stack                 String Pool

s -------------> "Java Programming"

                 "Java"
```

The original `"Java"` object still exists unchanged.

---

# Interview Definition

> An immutable object is one whose internal state cannot be modified after it is created. Any operation that appears to modify it actually creates a new object.

---

# 2. How is String Immutable?

String immutability is achieved through **multiple design decisions**, not just one.

---

## Reason 1: `String` is Final

Declaration

```
public final class String
```

This prevents inheritance.

Example

```
class MyString extends String { }
```

Not allowed.

Without `final`, a subclass could override methods like:

```
equals()

hashCode()

charAt()

substring()
```

and potentially change the behavior of `String`.

---

## Reason 2: Internal State is Private and Final

In Java 8:

```
private final char[] value;
```

In Java 9+:

```
private final byte[] value;

private final byte coder;
```

These fields:

- are `private`
- are `final`
- cannot be reassigned after construction

---

## Reason 3: No Setter Methods

Example

```
String s = "Java";
```

There is **no method** like:

```
s.setValue("Python");
```

All modifying methods return a **new String**.

Examples

```
replace()

concat()

substring()

trim()

toUpperCase()
```

---

## Example

```
String s = "Java";

String t = s.replace('J', 'P');
```

Memory

```
s -----> "Java"

t -----> "Pava"
```

Original String remains unchanged.

---

# Internal Implementation

Simplified version of `String`

```
public final class String {

    private final byte[] value;

    private final byte coder;

}
```

Characteristics:

- Final class
- Private fields
- Final fields
- No mutator methods

Together, these make `String` immutable.

---

# 3. Why is String Immutable?

This is one of the **most common interview questions**.

---

## Reason 1: Security ⭐⭐⭐⭐⭐

Strings are used in:

- Username
- Password
- URL
- File Path
- Database URL
- Socket Connection
- Class Loading

Example

```
FileInputStream file =
    new FileInputStream("/secure/data.txt");
```

If the file path could change after validation:

```
Check Permission

↓

Modify Path

↓

Access Another File
```

This would be a major security risk.

Immutability prevents such attacks.

---

## Reason 2: Thread Safety ⭐⭐⭐⭐⭐

Suppose

```
String s = "Java";
```

Thread A

```
System.out.println(s);
```

Thread B

```
System.out.println(s);
```

Since `String` cannot change,

both threads safely share the same object.

No synchronization is required.

---

## Reason 3: String Constant Pool ⭐⭐⭐⭐⭐

Example

```
String s1 = "Java";

String s2 = "Java";
```

Memory

```
s1 ------|

          |-----> "Java"

s2 ------|
```

If one reference changed the object,

the other reference would unexpectedly see the modified value.

Immutability makes sharing pooled objects safe.

---

## Reason 4: Performance ⭐⭐⭐⭐

Because Strings never change,

the JVM can safely:

- Reuse pooled objects
- Cache the hash code
- Optimize memory usage

---

## Reason 5: HashMap Compatibility ⭐⭐⭐⭐⭐

Example

```
HashMap<String, Integer> map = new HashMap<>();

map.put("Java", 100);
```

Internally

```
Hash("Java")

↓

Bucket
```

If `"Java"` could change to `"Python"`:

```
Hash Changes

↓

Bucket Changes

↓

Lookup Fails
```

Immutability ensures the hash code remains consistent for the object's lifetime.

---

# Benefits of Immutability

## 1. Security

Sensitive information cannot be modified after creation.

Examples

- Passwords
- URLs
- File names
- Database connections

---

## 2. Thread Safety

Immutable objects are inherently thread-safe because they cannot be modified.

---

## 3. Better Performance

The JVM can safely optimize immutable objects by:

- Sharing references
- Caching values
- Avoiding unnecessary copying

---

## 4. String Pool Compatibility

Multiple references safely point to the same pooled object.

```
String a = "Java";

String b = "Java";
```

Only one object is needed.

---

## 5. HashMap Compatibility

Hash codes remain stable throughout the object's lifetime.

# Can We Make String Mutable?

**No.**

The `String` class itself is intentionally immutable.

If mutable text is needed, Java provides:

- `StringBuilder`
- `StringBuffer`

---

## StringBuilder

```
StringBuilder sb = new StringBuilder("Java");

sb.append(" Programming");

System.out.println(sb);
```

Output

```
Java Programming
```

The same object is modified.

---

## StringBuffer

```
StringBuffer sb = new StringBuffer("Java");

sb.append(" Programming");
```

Also mutable, but **thread-safe** because its methods are synchronized.

---

# String vs StringBuilder vs StringBuffer

|Feature|String|StringBuilder|StringBuffer|
|---|---|---|---|
|Mutable|❌ No|✅ Yes|✅ Yes|
|Thread Safe|✅ Yes (immutable)|❌ No|✅ Yes|
|Performance|Good for read-only|Fastest for modifications|Slightly slower due to synchronization|
|String Pool|✅ Yes|❌ No|❌ No|

# Common Interview Questions

### 1. What is immutability?

An immutable object cannot have its state changed after it is created.

---

### 2. Is `final` alone enough to make a class immutable?

No.

A class should also:

- Have private fields
- Avoid setters
- Prevent exposing mutable internal state
- Initialize all fields during construction

---

### 3. Which methods modify a String?

None.

Methods such as:

- `concat()`
- `replace()`
- `trim()`
- `substring()`

always return a **new String**.

---

### 4. Why does `HashMap` prefer immutable keys?

Because changing a key's hash code after insertion would make the entry difficult or impossible to retrieve.

---

### 5. Why is the String Pool possible?

Because immutable objects can be safely shared by multiple references without any risk of accidental modification.

---

### 6. Which mutable alternatives are available?

- `StringBuilder` (fast, not thread-safe)
- `StringBuffer` (thread-safe, synchronized)

---

# Common Mistakes

### Mistake 1

Thinking `concat()` modifies the original String.

```
String s = "Java";

s.concat("8");
```

`"Java"` remains unchanged.

---

### Mistake 2

Believing `final` alone makes `String` immutable.

`final` only prevents inheritance. Immutability also depends on private final fields and the absence of mutator methods.

---

### Mistake 3

Assuming immutable means the reference cannot change.

```
String s = "Java";

s = "Python";
```

This is valid because the **reference** changes, not the original String object.

---

### Mistake 4

Thinking `StringBuilder` uses the String Constant Pool.

It does not. `StringBuilder` objects are regular heap objects and are mutable.

# 2-Minute Interview Answer

> A String is immutable, meaning its state cannot change after it is created. Java achieves this by declaring the `String` class as `final`, keeping its internal fields private and final, and not providing any methods that modify its contents. Operations like `concat()` and `replace()` create new String objects instead of changing existing ones. Immutability is essential because it improves security, allows safe sharing of objects in the String Constant Pool, makes Strings inherently thread-safe, enables hash code caching for better performance, and ensures that Strings work reliably as keys in collections such as `HashMap`. When mutable text is required, Java provides `StringBuilder` and `StringBuffer` instead of making `String` itself mutable.
